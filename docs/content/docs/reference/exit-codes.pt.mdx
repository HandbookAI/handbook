## Códigos de saída

| Código | Significado                                                                                            | Emitido por                           |
| :----: | ------------------------------------------------------------------------------------------------------ | ------------------------------------- |
|  `0`   | Sucesso                                                                                                | todos os comandos                     |
|  `1`   | Um erro: configuração inválida, um artefato ausente, uma execução que falhou, um endpoint inalcançável | todos os comandos                     |
|  `2`   | Uma **verificação** falhou — a ferramenta funcionou, e a resposta é não                                | `validate`, `apply`, `config --check` |

A distinção entre `1` e `2` é estrutural em scripts:

```bash
handbook validate --skill skills/api --source ~/code/api
case $? in
  0) echo "fresh" ;;
  2) echo "the handbook has drifted — schedule a resync" ;;
  *) echo "something is broken" >&2; exit 1 ;;
esac
```

### Quais comandos podem sair com 2

- **`validate`** — o pacote SKILL falhou em uma verificação estrutural, ou os hashes do fonte mudaram.
- **`apply`** — uma ou mais edições não foram aplicadas (`no-match`, `ambiguous`, `unsafe-path`, …).
  Em `--dry-run` isso significa "este plano não se aplicaria de forma limpa".
- **`config --check`** — uma configuração é inválida ou uma obrigatória está faltando.

O `plan` sai com **`1`** quando o planejador desistiu, e não com `2`: uma execução
abandonada é um erro, não uma resposta negativa.

## stdout versus stderr

| Fluxo      | Carrega                                                                                                                                   |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **stdout** | O resultado do comando, em JSON — exceto `plan` sem `--out`, que escreve o próprio plano, e `config` sem `--json`, que escreve uma tabela |
| **stderr** | Todo o log, todo o progresso, todos os avisos e cada mensagem de erro                                                                     |

Essa separação é o que torna o uso de pipes seguro:

```bash
handbook analyze --source ~/code/api --work work/api | jq .functions
handbook config --json | jq '.settings[] | select(.source.kind == "env") | .key'
handbook plan --source ~/code/api --request "…" > plan.md     # logs still visible
```

Os erros são prefixados para que sejam encontráveis com grep:

```text
handbook: error: invalid configuration:
  - source is required: pass --source, set HANDBOOK_GENERATE_SOURCE, or add it to handbook.config.yaml
```

## Níveis de log

| Como                       | Nível                      |
| -------------------------- | -------------------------- |
| padrão                     | `info`                     |
| `-v` / `--verbose`         | `debug`                    |
| `-q` / `--quiet`           | `error` — **vence o `-v`** |
| `HANDBOOK_LOG_LEVEL=debug` | `debug`, sem nenhuma flag  |

O `HANDBOOK_LOG_LEVEL` também afeta as duas linhas de bootstrap que reportam quais
arquivos `.env` e qual arquivo de configuração foram carregados — útil quando um valor
está vindo de algum lugar que você não esperava.

O `validate` é a exceção: ele escreve linhas legíveis por humanos no stderr e se comunica
através do seu código de saída.
