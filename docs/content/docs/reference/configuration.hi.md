यह पृष्ठ एक **जनरेटेड पेज का अनुवाद** है। अंग्रेज़ी मूल `pnpm run config:docs` द्वारा settings registry से जनरेट होता है और drift test से सुरक्षित है; यह अनुवाद हाथ से बनाए रखा जाता है — अंग्रेज़ी मूल बदलने पर इसे भी अपडेट करें।

## प्राथमिकता

हर setting उन्हीं परतों से होकर हल होती है, सबसे ऊँची प्राथमिकता पहले: **flag** > **shell env** > **`.env`** > **`handbook.config.yaml`** > **डिफ़ॉल्ट**। जो पहली परत मान देती है वही जीतती है और उस setting के लिए उसके नीचे की हर परत अनदेखी कर दी जाती है। यह देखने के लिए कि असल में क्या हल हुआ और वह किस परत से आया, `handbook config` चलाएँ — या केवल एक subcommand देखने के लिए `handbook config --command <name>`।

## नामकरण

registry में एक camelCase `key` एक साथ तीनों सतहों को चलाती है: एक flag, एक environment variable, और एक config-फ़ाइल key। इनमें से किसी के आगे कमांड का नाम लगाने से वह सतह एक subcommand तक सीमित हो जाती है, और तीनों पर यह वही रूपांतरण है — `HANDBOOK_<KEY>` बनता है `HANDBOOK_<COMMAND>_<KEY>`, और `key` बनता है `<command>Key`, चाहे वह सपाट लिखा हो या `<command>:` के नीचे एक स्तर nested। नीचे _(scoped)_ चिह्नित setting केवल उपसर्ग वाला env नाम स्वीकार करती है, क्योंकि उसका अर्थ हर कमांड पर बदलता है (`--out`, skill पैकेज में `--lang`)।

## Bootstrap

तीन शीर्ष-स्तरीय settings ऊपर की परतों की ओर इशारा करती हैं, और खुद registry के बाहर हैं, बाकी हर setting से पहले एक बार हल होती हैं — यही वजह भी है कि इनमें से कोई उसी चीज़ से सेट नहीं की जा सकती जिसे वह लोड करती है: `handbook.config.yaml` के भीतर एक `--env` key, `.env` के भीतर एक `--env-file` पंक्ति, या उसी फ़ाइल के भीतर एक `--config` key — इन्हें पढ़ने वाला कोई बचता ही नहीं।

- `--env <name>` (या `HANDBOOK_ENV`) प्रति-environment cascade चुनती है — तीनों में अकेली जिसके पास flag और environment-variable दोनों रूप हैं, क्योंकि यह किसी एक ठीक फ़ाइल की ओर इशारा करने के बजाय एक environment का नाम लेती है।
- `--env-file <path>` ठीक वही एक फ़ाइल लोड करती है, नीचे की cascade को छोड़कर।
- `--config <path>` ठीक एक config फ़ाइल का नाम लेती है, नीचे बताई environment-सजग खोज को छोड़कर (डिफ़ॉल्ट: working directory से ऊपर चलकर मिली निकटतम `handbook.config.yaml`-परिवार की फ़ाइल, repo सीमा पर रुकते हुए)।

### `.env` cascade

`--env-file` न हो तो CLI एक तय फ़ाइल के बजाय `.env*` फ़ाइलों की cascade लोड करती है, सबसे ऊँची प्राथमिकता पहले। मौजूदा `applyEnvFile` नियम — पहले से सेट key को कभी override न करना — ही वह चीज़ है जो cascade को इससे ज़्यादा कुछ नहीं बनाती कि "इन्हें इसी क्रम में बुलाओ, key सेट करने वाली पहली फ़ाइल जीतती है":

| #   | फ़ाइल               | कौन  | दायरा               | committed?        |
| --- | ------------------- | ---- | ------------------- | ----------------- |
| 1   | shell environment   | —    | —                   | हमेशा जीतता है    |
| 2   | `.env.<name>.local` | निजी | केवल यह environment | नहीं (gitignored) |
| 3   | `.env.<name>`       | टीम  | केवल यह environment | हाँ               |
| 4   | `.env.local`        | निजी | हर environment      | नहीं (gitignored) |
| 5   | `.env`              | टीम  | आधार रेखा           | हाँ               |

पंक्ति 2 और 3 तभी लागू होती हैं जब `--env`/`HANDBOOK_ENV` किसी environment का नाम ले। **दोनों में से कोई सेट न हो तो केवल पंक्ति 4 और 5 लोड होती हैं — ठीक वही जो इस cascade के आने से पहले लोड होता था, इसलिए बिना `.env.local` वाले किसी मौजूदा सेटअप में कोई बदलाव दिखता ही नहीं।**

### environment के साथ config-फ़ाइल खोज

`--config` को छोड़ दें तो खोज अब भी working directory से ऊपर चलती है और repo सीमा पर रुकती है, पर हर विज़िट की गई directory में वह अब पहले `handbook.config.<name>.{yaml,yml,json}` देखती है (केवल तब जब कोई environment नामित हो), उसके बाद सादी `handbook.config.yaml` वगैरह — इसलिए नामित फ़ाइल उसी directory में पड़ी सादी फ़ाइल को हमेशा हरा देती है, भले ही सादी फ़ाइल working directory के ज़्यादा पास वाले स्तर पर मौजूद हो। कोई environment नामित न हो तो खोज अपरिवर्तित रहती है।

यह देखने के लिए कि कौन-सा environment सक्रिय है और उसने ठीक कौन-सी फ़ाइलें लोड कीं, प्राथमिकता क्रम में, `handbook config` चलाएँ — चार मान-परतों के ऊपर एक cascade इतने संभावित स्रोत बना देती है कि उन्हें याद से ट्रैक नहीं किया जा सकता, और जिस परत को यह कमांड दिखा न सके वह उस परत से अलग नहीं जो काम ही न करे।

`readWorkers` के लिए हल किया उदाहरण (flag `--read-workers <n>`, डिफ़ॉल्ट `12`):

| सतह                        | सपाट                    | `generate` तक scoped             |
| -------------------------- | ----------------------- | -------------------------------- |
| env                        | `HANDBOOK_READ_WORKERS` | `HANDBOOK_GENERATE_READ_WORKERS` |
| `handbook.config.yaml` key | `readWorkers`           | `generateReadWorkers`            |

config-फ़ाइल के रूप आपस में बदले जा सकते हैं: सपाट `readWorkers: ...` और nested `generate: { readWorkers: ... }` का मतलब एक ही है, क्योंकि पढ़े जाने से पहले फ़ाइल उसी camelCase जोड़ से सपाट कर दी जाती है।

| `host`            | `--host <addr>`             | `HANDBOOK_HOST`                                | string                                  | `127.0.0.1`                 | bind पता; जब तक आप इसे सेट न करें यह loopback पर ही रहता है (containers को 0.0.0.0 चाहिए)। CSRF guard फिर भी loopback Host हेडर माँगता है                                                                  |
| `stateDir`        | `--state-dir <dir>`         | `HANDBOOK_STATE_DIR`                           | path                                    | —                           | studio.json और प्रबंधित work directories कहाँ रहती हैं; डिफ़ॉल्ट $HOME/.handbook-studio                                                                                                                    |
