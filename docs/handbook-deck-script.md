## 开场：先把三个词立住（不翻页，40 秒）

（站定，先别放幻灯片）

大家好，占用十几分钟。我先花半分钟把三个词讲清楚，不然后面我说的话你们听着会累。

第一个词，**调用图**。就是「谁叫谁」的一张接线图。它不是运行程序测出来的，是**不开机、只读代码**画出来的——像看一栋楼的接线图，不用通电就知道这个开关连着哪盏灯。

第二个词，**卡片**。这个工具给**每一个源码文件**配一张小卡片，上面写两件事：这个文件是干什么的；里面每个函数从第几行到第几行、都叫了谁。就像仓库里每个零件都贴一张标签。

第三个词，**手册**。把这些卡片按「这个系统是怎么跑起来的」顺序编成章节，再用人话写出来——就成了一本书。

（如果听众里有非技术同事，加一句）还有一个词：**agent**，指会自己动手改代码的 AI，不是只会聊天的那种。

好，开始。这个工具解决的是「文档永远过期」这个老问题，顺手也解决了 AI 改代码「改漏地方」的一半。

## 第 1 页 · 封面「每个仓库，自带一本活的手册」

（翻到封面，停两秒）

一句话：**给每个代码仓库配一本「活的」说明书**。

「活的」是两件事。第一，它不是人手写的，是**从代码里长出来的**。第二，代码改了它跟着改——而且只改被牵动的那几页，不是整本重写。

【举例】就像一本产品说明书，你换了个零件，它自动只重印那一页，其他页不动。

它伺候两种读者：**人**——拿到一本能看懂的说明书；**AI**——拿到一张改代码用的地图。两个都会给你们看真东西。

（过渡）先说为什么要做它。

---

## 第 2 页 · 痛点「我们每天都在为过期的文档买单」

（翻页，指三张卡从上往下）

三个场景，你们应该都眼熟。

第一个，**新人入职**。架构图是两年前的，wiki 半年没人动。最后怎么办？拉着老同事陪读三天代码。

【举例】新人问「订单状态到底在哪儿改的？」问到第三个人才问对——这三次打断，是三个人的时间。

第二个，**写文档的人最委屈**。文档写完那天就开始过期，而且没有任何机制把代码变更同步回来。慢慢地大家就默契地不看了。

第三个是新问题，**让 AI 改代码**。

【举例】你让 AI 把「手机号」字段加长。它改了注册接口——对的。但这个项目还有一条 Excel 导入的路径、短信模板里还写死了一个长度校验。**它不知道，用搜索也搜不全**，于是漏改，上线才发现。

（指底部虚线框）这三件事是同一个病根：**文档是手工拍的照片，代码是活的**。照片和活人之间的差距，每天都在变大。

（过渡）那市面上没有工具吗？有，但都缺一环。

## 第 3 页 · 对比「不是没有工具，是没有闭环」

（翻页，别逐格念，挑两列讲）

这页把常见做法摆一起，我只讲两列。

**「让大模型一次性生成文档」**——去年很流行。两个问题：模型凭印象写，**会编**；代码一变只能整本重生成，贵，而且每次生成的结构都不一样，没法跟上次对照着看。

【举例】相当于请人通读全书写一份读书笔记。笔记写完，书又改了——你只能请他重读一遍。

**「让 agent 现场读代码」**——这是现在的默认做法，Claude Code、Cursor 都是。它读的确实是真代码，这点比上面强。但它**每接一个任务都重新摸一遍**，摸完就忘。

【举例】就像每次进城都重新问路，问完不画地图。第二天再来，还得重新问一遍。

（指金色那列）Handbook 这列的区别就三条：事实是**读代码算出来的、带行号能验**；**每个文件都保证有一张卡片**；代码改了**只更新被牵动的那几章**。

（过渡）我知道你们心里在想什么——「那我直接用 Claude Code 不就完了？」下一页专门回答。

## 第 4 页 · 关键疑问「不是替代 Claude Code，是给它装外挂记忆」

（翻页，这页放慢，全场最重要的一页）

先把立场说清楚：**这东西不是 Claude Code 的对手，是给它配的外挂记忆。**

**第一，探索变沉淀。**

我要先说准确一点，免得被内行同事挑：agent 不是「把整个库读一遍」，它是**定向搜索**——搜一下、读几个文件、猜错、再搜一遍。真正贵的不是它读了多少字，是**来回的次数**。

【举例】为什么次数比字数贵？因为每问一轮，都要把之前所有对话**从头重发一遍**。你可以想成：每次找同事问事，都得先把前情复述一遍——第十次复述的那段话，比第一次长十倍。所以十轮的花费远不止一轮的十倍。

Handbook 把整个库**梳理一次**，之后全组每个任务都用同一份结果。而且它每次都是**一模一样的字节**，能吃到模型服务的缓存折扣；现场探索出来的临时内容每次都不同，永远吃不到。

【别念】token 可以粗略理解成「字数」，按字数计费。有人问再解释。

**第二，对话变资产。**

agent 在对话里想明白的事，对话一关就没了，别人也没法核对。手册里每个事实都带行号，**写错了任何人都能指出来**。

**第三，散落的改动点变清单。**

每一章开头有一块固定格式的「工位牌」，写着：这一章碰哪些全公司共用的东西、**改了这个源文件必须同时改哪个测试**、同一小组还有哪些文件、想新增同类照哪个文件抄。

【举例】就像修理工位上挂的牌子：这个工位负责什么、动它会牵连哪些工位、换这个零件必须同时换哪颗配套螺丝。

**空着也是结论**——这一章没写「共用的东西」，意思就是它不碰全局状态，你可以放心改。

我们这个仓库 20 章里，有 14 章列出了「源文件 ↔ 它的测试」这种必须同改的配对。

（这句一定要说，否则被追问会下不来台）**这里我主动说清楚边界**：这些配对是**照着接线图和文件命名推出来的，不读 git 提交历史**。所以手册自己在那一栏标了「编辑前请核实」。纯靠老员工口头传承的规矩——比如「改这里必须同步改另一个仓库的常量表」——**它抓不到**。

（过渡）那它整体怎么转？看下一页那张图。

## 第 5 页 · 闭环「生成 → 使用 → 回写」

（翻页，手沿着图从左往右走一遍）

从左往右：源码进来，先**不用大模型**，纯读代码，把「谁叫谁」抽成那张接线图。这一步是**免费的**，也是后面一切的地基。

然后大模型上场，在这些硬事实之上分章节、写人话，出两个产物：给人看的**手册站点**，给 agent 用的**地图**。agent 拿着地图，产出精确的改动方案，再由工具落到代码里。

（指红色虚线，加重）关键是这条红线：代码改完，跑一条命令，手册**只更新被牵动的那几章**。

【举例】像一本书改了三页，只重印这三页，不重印整本——所以它便宜、也快。

有人肯定要问：那手册自己会不会过期？**会——如果没人跑那条命令。** 所以建议把它挂到代码合并流程里，合并就自动更新。（仓库里还没有现成的配置，要自己加一小段。）这样「新鲜度」就从靠人自觉，变成靠流水线。

（过渡）看看东西长什么样。先看给人的。

## 第 6 页 · 给人的那一半「像读书一样读代码库」

（翻页，强调一句：**这是真实截图，不是示意图**，可以直接指着念）

这就是生成出来的手册，纯静态网页，双击就打开，不用部署。这一页是它**给自己这个仓库**写的第三章。

（指左边）左边是目录，20 章。注意它的顺序：不是按文件夹排的，是按**这个系统怎么跑起来**排的。

【举例】不是「a 文件夹、b 文件夹、c 文件夹」，而是「先开机装配、再解析代码、再干活、最后收尾打包」——像一本书的章节，从头读下来就知道这系统怎么转。

（指正文）中间这段话，我特别说一句：**这是模型写的，一个字没改**。它把一个很技术的东西解释成「语法字典」，把另一个解释成「插头转换器」。

【举例】「插头转换器」这个说法就是给新人看的文档该有的样子——你不用先懂那个技术名词，也能明白它干什么。

（指下面展开的那个文件）我把其中一个文件展开了。最下面那行写着 `discoverByExtension 行 54–62`：**每个函数都标了它在第几行**。这些行号不是模型写的，是程序数出来的，**模型没有权限改**。

【举例】所以核对特别便宜：手册说这个函数在 54 到 62 行干某件事，你翻过去看那 9 行代码，**30 秒就知道它有没有讲错**。文字可以写得平庸，但行号不会骗人。

（过渡）再看给 AI 的那一半。

## 第 7 页 · 给 AI 的那一半「agent 拿到的不是文档，是改码地图」

（翻页，左右两块分别讲）

（指左边）左边是给 agent 看的东西——就是刚才说的那块「工位牌」：这一章干什么、关键词是什么、碰哪些共用的东西、想新增同类照哪个文件抄、同组还有哪些文件。

agent 动手之前先看这张牌，就知道**这次要碰的范围有多大**。

（指右边）右边是它交出来的方案。注意它交的不是「你去改改 xx 文件」这种话，而是**逐字精确**的东西：这段旧代码、换成这段新代码。

这里有个安全设计值得单独说。真正落到文件里的那一步，是一个**很笨但很安全**的执行器。它拿着方案里那段「旧代码」去文件里找：

- 找不到 → **拒绝**，一个字都不改
- 找到**两处**一样的 → 也**拒绝**

【举例】像换零件前先比对旧零件的编号。编号对不上，不动手；发现有两个一模一样的编号，也不动手——因为它分不清该换哪一个，**这时候猜就是灾难**。

而且整份方案是**全成或全不成**，写之前先备份，可以还原到改动前的一模一样的状态。也可以先「试装」——只比对不真改。

（过渡）听到这儿你们可能在想：这么多环节靠大模型，靠得住吗？下一页讲我们怎么防它。

---

## 第 8 页 · 为什么敢信「三道防线」

（翻页，三张卡从左到右）

**第一道：把「事实」和「说法」分开。**

【举例】这本手册是**一个测量员和一个作家合写**的。测量员负责量数字：这个函数在第几行、它叫了谁——量完直接进档案。作家负责在旁边写故事：这个函数像流水线上的工人。**关键的制度是：作家没有档案的写入权限。** 模型哪怕在回复里信誓旦旦说「这个函数在第 999 行」，那个数字也根本没有入口能写进手册。

读不出来的调用怎么办？**单独存到一个「存疑」文件里，不硬塞进接线图假装知道。**

**第二道：章节结构不是模型一口气写的，是「吵」出来的。**

一个角色先出方案，另外三个角色分别从三个角度挑刺：一个看**代码对不对**、一个看**结构合不合理**、一个看**新人读不读得懂**。三个都通过、再过一遍机械校验，才算数。

（指小柱状图）这是真实记录：我们这个仓库 93 个文件，第一轮有 **25 个文件不知道该归哪一章**；第二轮采纳了 2 处结构调整，全部归位；第三轮没有新改动，说明稳定了。

**第三道：出问题就降级，不整锅端。**

【举例】像流水线上某台机器卡住了，不是停整条线，而是走人工备用工序——**但报表上会写明这批货是备用工序出的**。

这里最关键的一句：**失败一定会被记在账上，不会偷偷装成成功。**

（过渡）讲了这么多机制，它到底真跑通过一次没有？下一页是实录。

## 第 9 页 · 闭环实录「一次真实改动，每一环都留了记录」

（翻页，这页放慢，一格一格指）

前面都在讲它长什么样。这页讲**它真的跑通过一次**，而且每一步都留了记录，你们可以当场查。

（指①）**需求就一句话**：「修复回复解析：空返回、被截断、格式不对，都不能再被当成成功」。这句话是原文，就存在记录里。

（指②）**定位**：手册告诉我这次会牵动 4 章。我没有靠猜、也没有靠搜——是手册算出来的。

（指③）**方案**：那个只读的 AI 去看真实代码，给出「旧代码 → 新代码」的逐字方案。

（指④）**真正改到代码里**：先「试装」——只比对不动手。找不到、或者找到两处，都拒绝。全成或全不成，写之前先备份。

（指⑤）**回写**：这次改动一共牵动 5 个文件，**没有新增、也没有删除任何文件**。

【举例】这一点值得停一下：我只是改了几个函数**里面**的代码——文件名没变、文件个数没变、行数也差不多。以前这种改动是**看不出来的**。现在它给每个文件算一个「指纹」，内容一改指纹就变，所以一个不漏地抓到了 5 个。

抓到之后，只重做这 5 张卡片、只重写这 4 章，其他章节直接用上次的结果，**一分钱不花**。

（指底部那行）最后这条记录我特别喜欢：我先让它把改动真正写进了代码，然后**故意又手工改了那个文件**，再去点「回滚」——它**拒绝了**，因为它不知道我后来那次手改要不要保留。加了强制参数才还原。

**宁可拦住你，也不悄悄吃掉你的工作。**

（过渡）这些都是命令行。不想敲命令的话，还有个界面。

## 第 10 页 · Handbook Studio「不想敲命令」

（翻页，两张都是真实界面截图，直接指）

一条命令起个本机网页，浏览器打开就是这个。

（指上面那张，中间那块）这里我要重点说一个细节，因为它是我们**踩过坑之后**加的。

上面写「已归档 100%」——「归档」就是**每个文件都分到了某一章**；下面那行金色的写「**已描述 91/93，2 个是空卡片**」。为什么要并排放两个数？

【举例】就像图书馆：「每本书都上架了」是 100%——这个数**永远是满的**，因为每本书总能塞进某个书架。但「每本书都写了内容简介」才是 91/93。**上架不等于有简介。**

以前这里只显示前面那个数。结果有一次，90 个文件的简介**全是空的**，界面上却显示 100%，任务还报告成功。所以现在两个数必须并排显示，而且**一旦不满就标黄**。

（指下面那段中文）这段是它给自己写的系统总览，一个字没润色。

（指下面那张）这是**影响图**。一个圆点是一个文件，**圆越大说明被叫得越多**；线是文件之间的调用；颜色是所属章节。点任何一个圆点，直接跳进源码，带行号。

【举例】改代码前想知道「我碰这个文件会牵动谁」，看这张图比翻代码快得多。

（指右边）三件事顺带说清：它**只在你自己电脑上跑**，页面不向外发任何请求，源码只发往你自己配的那一个模型服务；生成任务在后台跑、日志实时看；除了这两个视图，还有源码、演化、历史三个。

（指最后一条）最后是**真实花费**：93 个文件全量精读，卡片阶段 93 次请求、一分四十八秒。同一个模型服务，**关掉「思考」大约 3 分钟，开着「思考」要 40 分钟以上**——差十几倍。所以接服务的时候记得看这个开关。纯读代码那一步永远免费。

（过渡）到这儿你们可能觉得我一直在自夸。下一页把话反过来说。

## 第 11 页 · 可验证性「别信我，自己核」

（翻页，语气放平，这页是交底）

这页只有一个意思：**你不用相信我，这四件事你自己就能验。**

**第一，30 秒就能戳穿一个错误。** 手册说某个函数「循环取任务直到队列空」——你翻到那个文件第 10 行，看四行代码。对就是对，错就是错。

**第二，我们自己的评审记录都在仓库里。** 一共 9 轮、133 个问题，报告都在，每个问题还附了能跑的复现脚本。想知道这东西哪儿坏过，不用问我，自己翻。

# 附：七个硬问题的详细解答（**不用念**，被追问时翻这里）

> 上面正文里我把这些都简化成了例子。如果现场有人往深处问——「到底怎么静态分析的」
> 「凭什么说每个函数都有行号」——翻到这里，每一节都有具体代码和真实数据。

## 1. 静态分析是怎么"静态"分析的？能全覆盖吗？

"静态"的意思：不运行你的代码，只"读"代码。 像一个不插电的审稿人，把源文件当文本拿来解析。

具体分两遍：

第一遍：登记造册。 用 tree-sitter（一个工业级语法解析器，Chrome/GitHub 都在用的那类技术）把每个文件解析成语法树，然后逐个登记：这个文件里有哪些类、哪些函数、每个函数从第几行到第几行、参数写了什么类型注解、self.xxx = yyy 给对象挂了什么属性。比如扫 worker.py 时登记：Worker 类有 run、execute 两个方法；构造函数里 self.queue = queue，而参数 queue 的注解是 TaskQueue——于是"学到"self.queue 是个 TaskQueue。

第二遍：顺藤摸瓜。 拿着第一遍的名册，再看每一处函数调用长什么样，套四条规则去认（下面第 4 题详细讲）。

覆盖率，分两层说，很重要：

文件层面：全覆盖，且是"保证"级别的。 只要是支持的 5 种语言（Python/TS/Go/Rust/Shell）的文件，每一个都会被扫描、登记在案，后面每个文件必有一张文档卡片——就算某一步失败了，也会留一张空卡片并把这个文件记进"缺失名单"（_coverage.json），绝不静默跳过。
调用关系层面：诚实地不追求 100%。 有些调用静态分析确实认不出来，比如 Python 里 getattr(obj, name)() 这种动态调用，或者一个局部变量的方法。认不出来的怎么办？单独隔离到 dropped-calls.json 存档、分好类（内置函数/局部变量方法/裸名字……），不混进调用图里装作知道。图里的每条边都是有把握的。
另外两个边界：不支持的语言文件（.java、.json、.md 等）不进调用图；测试文件、vendor、node_modules 这类默认跳过。

## 2. 每个文件都有文档？每个函数都有？都有行号？

每个文件：有，保证有。 上面说了，"每文件一张卡片"是构造上保证的，缺了会显式记账。

每个函数：条目一定有，散文尽力有。 这句话是理解整个系统的钥匙。每个函数的文档条目分两半：

结构那一半（一定有，程序填的）：函数名、签名、起止行号、它调用谁、谁调用它、调了哪些外部库。这些从调用图里直接搬过来，不经过大模型的手。
散文那一半（尽力有，模型写的）：干什么用（purpose）、数据怎么流（data_flow）、调用关系的人话解释（relations）。deep 模式下模型逐个函数写；如果模型那次抽风没写出来，这三个字段可以是空的，但条目本身和行号还在。
每个函数都有行号记录：是的。 看真实例子，这是 demo 项目里 Worker.run 在调用图里的登记：

"app.worker.Worker.run": {
"file": "app/worker.py",
"lineStart": 10, "lineEnd": 13,
"signature": "def run(self)",
"className": "Worker", ...
}
第 10 到 13 行，解析器量出来的，手册里显示的"（lines 10–13）"就是它。

## 3. "每个事实带行号，写错了谁都能指出来"是什么意思？

意思是：手册给了你"核对答案的页码"。

传统 AI 生成的文档最大的问题是——它说错了你都不知道，因为你没法核对：它说"这个函数会重试三次"，你想验证，只能自己通读源码，成本高到没人去验，于是错误就一直留着。

Handbook 的手册里，每个函数条目都挂着"第 10–13 行"这种锚点，而这个锚点不是模型写的，是解析器量的。于是核对变得很便宜：手册说"Worker.run 会循环取任务直到队列为空"，你不信？打开 worker.py 翻到第 10 行，四行代码扫一眼——对就是对，错就是错，任何人 30 秒能戳穿一个错误。

所以那句话的完整含义是：散文（模型写的部分）可能讲得不好，但每句话旁边都贴着地址，验错成本从"通读全库"降到"按行号抽查"——这就使得错误留不住，因为发现太容易了。

## 4. 调用关系是怎么抽成"一张调用图"的？

拿真实例子走一遍。demo 项目里 Worker.run 的代码是：

def run(self): # 第 10 行
while self.queue.size() > 0: # 第 11 行
task = self.queue.pop() # 第 12 行
self.execute(task) # 第 13 行
第二遍扫描到这三处调用时，套规则去认：

self.execute(task) → 形状是"self.方法名()"→ 查名册：Worker 类自己有 execute 方法吗？有 → 记一条边：Worker.run → Worker.execute，类型 self_method（调自己的方法）。
self.queue.pop() → 形状是"self.属性.方法名()"→ 查第一遍学到的：self.queue 是什么类型？TaskQueue → TaskQueue 有 pop 吗？有 → 记边：Worker.run → TaskQueue.pop，类型 self_attr_method（透过成员对象调过去）。
类似还有两条规则：参数方法（参数注解了类型就能顺着认下去——demo 里 `Worker.__init__(self, queue: TaskQueue)` 正是靠这条让 `self.queue` 有了类型）和 import 追踪（from pkg import helpers; helpers.do() 能认出指向我们自己的 pkg/helpers.py，而 os.getpid() 认出是外部边界调用）。
认不出的（比如 print()）→ 丢进隔离区，不进图。
每认出一条，就记下"谁 → 谁、第几行、是不是 await"。全库扫完，把所有函数节点 + 所有边攒起来，就是 graph.json——这就是那张图。看它记下的真实内容：

{ "callerId": "app.worker.Worker.run", "calleeId": "app.queue.TaskQueue.pop",
"callType": "self_attr_method", "line": 12, "raw": "self.queue.pop" }
所谓"一张图"，就是几百上千条这样的边 + 节点表。后面一切都吃这张图：章节按它排顺序、函数文档的"谁调用谁"从它来、agent 地图的联动提示也从它来。

## 5. "给 agent 用的 SKILL 地图"生成了什么？在哪？怎么看？

生成的是一个文件夹的 markdown 文件，两种形态：

形态一：agent 定位索引（跑 handbook render --agent-site 时生成）
位置：<work目录>/handbook/agent/，比如你仓库里现成的：

examples/work/self/handbook/agent/
├── how_to_use.md ← 教 agent 怎么用这本手册的"操作规程"
├── index.md ← 所有章节的定位块汇总
├── disambiguation.md ← 重名词消歧（搜"parser"会命中哪几章）
└── <章节id>.md ← 每章一页
形态二：SKILL 技能包（跑 handbook skill 时生成），就是把手册重新打包成 Claude Code 能直接挂载的标准技能格式：SKILL.md + references/ 文件夹。demo 的成品在 examples/work/demo/skill/。

怎么看：全是普通 markdown，任何编辑器/IDE 直接打开。 比如 how_to_use.md 的真实开头长这样：

一份定位索引：告诉你东西在哪里、下一步该读什么。每条事实都锚定到文件路径、阶段 id 或寄存器 id。……不是代码的替代品。跳转过去并 Read 真实文件——手册可能过时；代码是唯一的事实来源。

所以"地图"不是什么可视化大图，就是一组结构固定、字段可靠、agent 读起来极其省 token 的 markdown 索引页。

## 7. "事实和叙述分层"，大白话展开

打个比方：这本手册是测量员和作家合写的。

测量员（静态分析）负责量数字：这个函数在第 10 行、它调用了那三个函数、这个类有这几个属性。量完直接进档案。
作家（大模型）负责在档案旁边写故事："这个函数像流水线工人，从队列取一个任务干一个"。
关键制度是：作家没有档案的写入权限。

落到代码层面是这么实现的：每个函数的文档条目，结构字段（行号/签名/调用关系）由程序从 graph.json 里直接复制进去；模型返回的 JSON 里，只有 purpose、data_flow、relations 三个散文字段会被合并进条目——它哪怕在回复里信誓旦旦说"这个函数在第 999 行"，那个数字也根本没有入口能写进手册。

为什么这个分层是"防线"？因为大模型的毛病是一本正经地编造细节，而它最爱编的恰恰是行号、函数名、调用关系这类"看起来很具体"的东西。分层之后：

编不了事实——事实通道物理隔离；
散文写烂了——顶多是"讲得平庸"，而且旁边就贴着行号（第 3 题），一查便知；
连"解析失败"都不许它补——认不出的调用进隔离区，宁可承认不知道，也不让模型猜。
一句话总结：能验证的部分绝不交给模型，交给模型的部分永远可验证。 这就是第一道防线。
