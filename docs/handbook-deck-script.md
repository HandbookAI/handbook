> 配合 `docs/handbook-deck.html` 使用：投屏放幻灯片，你看这份稿子。

## 开场（还没翻页时，10 秒）

大家好，今天占用大家十分钟，讲一个我最近在做的工具。先说结论：它解决的是"文档永远过期"这个老问题，而且顺便把 AI 改代码"改漏地方"的问题也解决了一半。往下看。

---

## 第 1 页 · 封面「每个仓库，自带一本活的手册」

（翻到封面，停两秒让大家看标题）

这个工具叫 Handbook。一句话：**给每个代码仓库配一本"活的"手册**。

"活的"是什么意思？两层：第一，它是从源码里**生成**出来的，不是人手写的；第二，代码变了它跟着变，**增量更新**，不用重写。

它同时服务两种读者：**人**，拿到一本能看懂的系统说明书；**AI agent**，拿到一张改代码用的地图。这两个后面都会演示。

（过渡）先说为什么要做这个东西。

---

## 第 2 页 · 痛点「我们每天都在为过期的文档买单」

（翻页，指着三张卡从上往下）

这页三个场景，大家应该都眼熟。

第一个，新人入职：架构图是两年前的，wiki 半年没更新，最后怎么办？拉着老同事**陪读三天代码**。老同事的三天也是钱。

第二个，写文档的人最委屈：文档写完那一天就开始过期，又没有任何机制把代码变更同步回来，慢慢地大家就默契地——**不看了**。

第三个是新问题，这两年才有的：让 AI 改代码。agent 改了 JSON 解析器，但这个项目还有个镜像的 XML 解析器，还有两处提示词模板里写死了格式——**它不知道，文本搜索也搜不全**，就漏改了。

（指底部虚线框）这三件事其实是同一个病根：**文档是手工拍的快照，代码是活物**。快照和活物之间的差距每天都在变大。

（过渡）那市面上没有工具吗？有，但都缺一环。

---

## 第 3 页 · 对比「不是没有工具，是没有闭环」

（翻页，别逐格念表，挑重点讲）

这页把常见方案摆在一起。重点看两列。

「让 LLM 一次性生成文档」——去年很流行。问题两个：模型凭印象写，**会编**；代码一变，只能整本重新生成，贵，而且每次生成的结构还不一样，没法对照。

「Agent 现场读代码」——这是现在大家的默认方案，Claude Code、Cursor 直接读。它读的确实是真代码，但**每接一个任务都从零探索一遍**：重复烧 token，上下文窗口也装不下整个大库，而且这次探索的结论，下次任务用不上，全浪费了。

（指金框列）Handbook 这列的差别：事实来自**静态分析**、逐条带行号可以验证；每个文件**保证**有卡片；代码变了 **resync 增量更新**；agent 直接能用。

（过渡）我知道大家心里在想什么——"那我直接用 Claude Code 不就行了？"下一页专门回答这个。

---

## 第 4 页 · 关键疑问「不是替代 Claude Code，是给它装外挂记忆」

（翻页，这页放慢，是全场最重要的一页）

先把立场说清楚：**Handbook 不是 Claude Code 的对手，是给它配的外挂记忆**。三个差别：

第一，**探索变沉淀**。agent 每接一个任务都要重新定位一遍——grep、读文件、猜错、再来一遍，读完就忘。这里要说准确一点：它不是"读整个库"，它是定向搜索；真正贵的是**轮次**，因为每一轮都会把整段对话重发一次，成本随轮次快速放大。而整个库本来也装不进上下文窗口——这个仓库的源码约 16 万 token。Handbook 把整库梳理一次，之后全队每个任务复用同一份结果；而且它字节稳定，能吃 prompt 缓存，探索产生的临时内容永远吃不到。

第二，**对话变资产**。agent 在对话里得出的结论，随着对话结束就没了，也没法核对；手册的每个事实带行号，写错了谁都能指出来。

第三，**散落的改动点变清单**。定位块用固定字段告诉你：这章碰哪些全局状态、**改了源文件必须同步改哪个测试**、同一子组还有哪些文件、新增同类照哪个范本写。**字段为空同样是结论**——这章没有需要担心的全局状态。本仓 20 章里有 14 章列出了源文件↔测试的强共变配对，比如 `llm/src/client.ts ↔ llm/src/client.test.ts`。

这里我要主动说清楚边界，免得被追问时下不来台：这些字段是**按调用图和命名推导**出来的，不读 git 历史。所以手册自己在字段上标了「编辑前请核实」。纯靠口头传承的约定——比如"改这里必须同步改另一个仓库的常量表"——它抓不到。谁要是问"那部落知识呢"，答案是：这版还没有，要抓得读 git 的共同变更历史。

（过渡）那它整体是怎么转起来的？看下一页这张图。

## 第 5 页 · 闭环「生成 → 使用 → 回写」

（翻页，手沿着图从左往右走一遍）

从左往右：源码进来，先做**静态分析**——这一步不用大模型，纯解析，把整个库的函数、调用关系抽成一张调用图，这是"事实层"。

然后大模型上场，在事实之上分章节、写大白话叙述，生成两个产物：给人看的**手册站点**，给 agent 用的 **SKILL 地图**。agent 拿着地图做出**精确变更**。

（指红色虚线，加重语气）关键是这条红色的回路：代码改完，跑一条 resync 命令，手册**增量前滚**——只更新受影响的章节，不用重新生成整本。

有人会问：那这手册自己会不会过期？会——**如果没人跑 resync**。所以建议把它挂成 CI 任务，合并即更新（仓库里还没有现成的 workflow，要自己加一个 job）。手册的新鲜度就从"靠自觉"变成了"靠流水线"。

（过渡）看看产物长什么样。先看给人的。

---

## 第 6 页 · 给人的那一半「像读书一样读代码库」

（翻页，指着仿真浏览器窗口）

这就是生成出来的手册站点，纯静态 HTML，双击就能打开，不用部署。

左边是章节目录，按系统的**执行顺序**排的——从启动、到解析、到主循环，像一本书的目录，不是按文件夹瞎排的。

（指正文）中间这段话，我特别说明一下：**这是模型真实生成的，一个字没改**。它把 tree-sitter 的 WASM 语法包解释成"语法字典"、把适配器解释成"插头转换器"——这是给新人看的文档该有的样子，不是给编译器看的。

（指函数卡片）往下每个函数带**行号**，这些行号和调用关系来自静态分析，模型无权改。所以叙述可以平庸，但**锚点不会说谎**——讲错了你顺着行号一查就知道。

（过渡）再看给 AI 的那一半。

---

## 第 7 页 · 给 AI 的那一半「agent 拿到的不是文档，是改码地图」

（翻页，左右两块分别讲）

左边是 SKILL 地图里一个章节的"定位块"：这章负责什么、入口概念是什么、碰哪些全局状态、新增同类照哪个范本写、同一子组还有哪些文件（这一项标了"编辑前请核实"）。agent 改代码之前先查这张图，就知道**影响范围**了。

右边是规划输出：agent 用手册定位以后，去读真实源码确认，最后输出的是**逐字精确**的编辑计划——旧代码块、新代码块、外加一份机器可读的变更声明。

这里有个安全设计值得一提：落盘由执行器（`handbook apply`）来做，旧代码块是**逐字节匹配**的——找不到、或者在文件里找到两处，都算**拒绝**。整份计划全成或全不成，写盘前先备份，可以还原到改前的确切字节。如果实际代码对不上——比如别人先改过了——它宁可失败也不改错地方。可以先 `--dry-run` 空跑，只核对不写。

（过渡）听到这大家可能会想：这里面这么多环节靠大模型，靠谱吗？下一页讲我们怎么防它。

---

## 第 8 页 · 为什么敢信「三道防线」

（翻页，三张卡从左到右）

第一道防线刚才说过了：**事实和叙述分层**。行号、调用关系这些硬事实来自静态分析，模型只写散文，碰不到事实层。解析不了的调用我们也不硬塞，单独隔离存档。

第二道有意思：章节结构不是模型一口气生成的，是**评审出来的**。内部有个"骨架医生"循环——一个角色提方案，三个角色（工程师、架构师、读者）并行挑毛病，机械校验通过才落地。（指小柱状图）这是真实记录：本仓 93 个文件，第 1 轮有 25 个不知道该归哪章，第 2 轮采纳 2 处结构改动后全部归位，第 3 轮没有新改动、确认收敛。

第三道，**降级而不是崩溃**：任何一步模型抽风，都有确定性的备胎方案顶上；失败会被如实记进覆盖率报告，不会偷偷装作成功。

（过渡）讲了这么多机制，它到底跑通过一次没有？下一页是实录。

---

## 第 9 页 · 闭环实录「一次真实改动，每一环都留了记录」

（翻页，这页放慢，一格一格指）

前面讲的都是它长什么样，这页讲**它真的跑通过一次**。五格从左到右，是一次改动的完整链条。

① **需求**就一句自然语言——「修复回复解析与预算处理：空返回、截断、形状漂移不再被当成成功」。这句话是原文，写在演化记录里。

② **定位**：手册告诉我这次牵动 4 个章节——演员-评论家审查、横切基础设施、叙事与寄存器提取、测试与夹具。我没有去猜，是手册算出来的。

③ **计划**：planner 只读源码，输出 old/new 的逐字节文本块，外加一份机器可读的变更声明。第 7 页那个真实的定位块就是它用来路由的东西。

④ **落盘**：先 dry-run 逐条核对。这里有个细节值得说——**找不到锚点算拒绝，在文件里找到两处也算拒绝**。为什么？因为找到两处说明它分不清该改哪一处，这时候猜就是灾难。全成或全不成，写盘前算 sha256 备份。

⑤ **前滚**：delta 是 5 changed、0 added、0 deleted——**注意这 5 个文件我只改了函数体，没有增删任何文件**，它靠内容哈希发现的。然后只重生成这 5 张卡片、只重写这 4 章，其余章节走缓存，一分钱不花。

（指底部那行）最后这条守卫记录是补丁执行器的实测：apply 落盘之后，**我故意又手改了那个文件**，再去回滚——它拒绝执行，报 skipped，因为它不知道我那次手改要不要保留。加 `--force` 才字节还原。宁可拦住你，也不悄悄吃掉你的工作。

①②⑤ 三处数字取自同一条真实演化记录，路径就写在页面上，有人不信可以当场打开那个 JSON。

（过渡）这些都是命令行。如果不想敲命令，还有个界面——下一页。

## 第 10 页 · Handbook Studio「不想敲命令」

（翻页，两张截图都是真实界面，直接指）

这是个跑在本机的 Web 界面，`handbook studio` 一条命令起来，浏览器打开 127.0.0.1。

（指上面那张）这是**总览**。左边状态就绪、20 章；中间覆盖率这块我要特别说一句：上面写「已归档 100%」，下面那行金色的写「**已描述 91/93 · 2 个为空卡片**」。为什么要并排显示两个数？因为「已归档」是靠调用图算的，它永远是满的——每个文件总能塞进某一章；只有「已描述」才说明有多少文件真的拿到了叙述。**如果只显示前面那个，一本空壳手册看起来也是 100%。** 我们踩过这个坑，下一页会讲。

下面那段中文是它给自己写的系统总览，一个字没润色；再往下是阶段索引，每章一句话。

（指下面那张）这是**影响图**。一个圆点是一个文件，半径按调用度——越大说明越多人调它；连线是跨文件调用；颜色是所属章节。点任何一个点，直接跳进源码视图，带行号和函数索引。改代码前想知道「碰这个文件会牵动谁」，看这张图比翻代码快。

（指右边四条）三件事顺带说清楚：它**只绑 127.0.0.1**，页面零外部请求，源码只发往 .env 里那一个端点——它是桌面工具，不是要部署的服务；生成、重新生成、免费分析都是后台作业，日志实时推；除了这两个视图，还有源码、演化、历史三个。

最后那条是**实测成本**：本仓 93 个文件、deep 全量，卡片阶段 93 次调用一分四十八秒，归档 7 秒，章节组织 18 次调用 9 秒。同一个端点，关掉「思考」约 3 分钟、开着思考 40 分钟以上——差 10 倍以上，所以接端点时记得看这个开关。静态分析永久免费。

（过渡）到这儿你可能觉得我一直在自夸。下一页把话反过来说。

## 第 11 页 · 可验证性「别信我，自己核」

（翻页，语气放平，这页是交底）

这页只有一个意思：**你不需要相信我，这四件事你自己就能验。**

第一，**30 秒戳穿一个错误**。每个函数条目挂着行号，而行号是解析器量的、模型碰不到。手册说 `Worker.run` 循环取任务直到队列空——你打开 `worker.py` 翻到第 10 行，四行代码，对就是对，错就是错。散文可以写得平庸，锚点不会说谎。

第二，**评审记录在仓库里**。9 轮对抗式评审、133 项发现，报告全在 `docs/internal/review/`，每条发现都附可运行的复现脚本。想知道这东西哪里坏过，不用问我，自己翻。

第三，**离线跑通，零 token**。`bash examples/run-demo.sh` 走内置 mock，不联网、不花钱，端到端出一本手册加一个 SKILL 包。不用先信我才能试。

第四，**过期它自己会说**。SKILL 里存了每个源文件的内容哈希，`handbook validate` 重算一遍就能点出哪几页已经落后于代码——它不会装新鲜。

（指下面那个虚线框）然后是边界，我们不装：小仓库不划算，几十个文件直接读更省；目标有字面量可搜的时候，`grep` 无敌，不用绕这一圈；**过期的手册比没有手册更贵**，因为它会把人和 agent 引到错地方——所以 resync 必须有人跑；叙述质量取决于你接的模型，但行号和调用关系不受影响；纯靠口头传承的约定它抓不到，因为它不读 git 历史；还有，本仓有 2 个文件被服务商网关按内容拦下了，我们没绕过——如实降级成空卡片，并在覆盖率里点名。

（过渡）说到「坏过」，下一页就是那次。

---

## 第 12 页 · 一次真实的失败「它坏过一次」

（翻页，这页别赶，讲故事）

这是前几天真实发生的一次。

（指左边）**症状**：在 Studio 点「重新生成」，作业报告成功。但打开一看，90 个文件的卡片**全是空的**，覆盖率 0/90。作业说成功，产出是空壳。

**我第一反应是错的**：以为端点坏了。于是去实测同一个端点——单条请求正常；16 路并发，16 个全部成功；更关键的是，骨架合成和章节组织在**同一次运行里**产出了真实的中文内容。所以端点没问题，只有「卡片」这一条路径在失败。

**真相**是：模型答对了，是我们的**解析层太窄**，把正确答案当成了失败。

（指右边）同一个根因，一共现身六次。空 `content` 被当成成功返回，不重试也不报错。中文散文里一个未转义的引号毁掉整段 JSON，然后扫描器抢到一个恰好合法的**嵌套碎片**当答案。解析只认一种形状，另外还有 5 处同病。截断的回复被当成完整答案。网络断了一下，把「0 条寄存器」**写进了缓存**，之后每次运行瞬间返回 0、一行日志都不打。最后一个最典型：模型把字段写成 `semantic`（单数），我们只认复数，**20 条完全正确的寄存器就这么静默蒸发了**。

修完之后：0/90 变成 **91/93**——分母从 90 变 93 是因为这中间仓库又多了 3 个文件；剩下那 2 个是被服务商网关按内容拦下的，那个我们没绕。

（指下面虚线框）留下两条规则，我认为比这次修的代码更值钱：

第一，**解析层不能比模型的真实输出更窄**。而且「收到但用不上」的条目必须计数并说明原因——**沉默本身就是缺陷**。现在全部文件都失败时，作业会直接失败，而不是渲染一本空壳手册给你。

第二，**测试全绿掩盖了坏产品**。夹具是按我们的预期造的——夹具里写 `engine_test.ts`，真实世界是 `client.test.ts`，所以那个字段在真实仓库上一次都没生效过，测试却一直是绿的。现在的规矩是：夹具必须来自真实回复。

（过渡）好，最后一页。

# 附：现场答问小抄

**Q：叙述会不会一本正经地胡说八道？**
A：散文有可能平庸，但每个事实带行号，错了能立刻定位；而且章节结构经过三角色评审 + 机械校验，结构性胡说会被拦住。讲错的部分，resync 或者手工改卡片都能修。

**Q：大仓库（几千文件）能用吗？**
A：架构上就是为大库设计的——文件级卡片、批量并发、断点续跑。建议先 analyze（免费）看规模，再 brief 试算，deep 只给核心目录上。

**Q：跟 DeepWiki / 其他 AI 文档站有什么区别？**
A：两个本质差别——事实层是静态分析出来的、逐条可验证，不是模型通读硬写；有 resync 闭环，代码变更后增量更新，不是一次性生成完就死了。

**Q：为什么不直接用更长上下文的模型把整个库塞进去？**
A：塞得进去也留不下来——每次任务都要重新塞、重新烧钱，而且结论没有沉淀、没法团队复用。手册是一次梳理、全队复用、持续更新。

**Q：生成一次要多久？**
A：取决于仓库大小和端点速度，差别可以很大。这个 93 文件的仓库实测：端点关掉「思考」时全流程约 3 分钟；同一端点开着思考（它为 900 字的答案写 3 万字思考）要 40 分钟以上。纯静态分析不用模型，秒级。

**Q：支持 Java / C++ 吗？**
A：还没有，加一门语言 = 写一个 adapter 文件（132–563 行，有五个现成模板照抄）。有需求的话排期做。

**Q：怎么防止它把敏感代码发出去？**
A：它只会请求 .env 里配置的那一个端点，没有别的出口；接内网端点就完全不出网。CI/演示用内置 mock，零外发。不放心可以抓包验证。

## 1. 静态分析是怎么"静态"分析的？能全覆盖吗？
"静态"的意思：不运行你的代码，只"读"代码。 像一个不插电的审稿人，把源文件当文本拿来解析。

具体分两遍：

第一遍：登记造册。 用 tree-sitter（一个工业级语法解析器，Chrome/GitHub 都在用的那类技术）把每个文件解析成语法树，然后逐个登记：这个文件里有哪些类、哪些函数、每个函数从第几行到第几行、参数写了什么类型注解、self.xxx = yyy 给对象挂了什么属性。比如扫 worker.py 时登记：Worker 类有 run、execute 两个方法；构造函数里 self.queue = queue，而参数 queue 的注解是 TaskQueue——于是"学到"self.queue 是个 TaskQueue。

第二遍：顺藤摸瓜。 拿着第一遍的名册，再看每一处函数调用长什么样，套四条规则去认（下面第 4 题详细讲）。

覆盖率，分两层说，很重要：

文件层面：全覆盖，且是"保证"级别的。 只要是支持的 5 种语言（Python/TS/Go/Rust/Shell）的文件，每一个都会被扫描、登记在案，后面每个文件必有一张文档卡片——就算某一步失败了，也会留一张空卡片并把这个文件记进"缺失名单"（_coverage.json），绝不静默跳过。
调用关系层面：诚实地不追求 100%。 有些调用静态分析确实认不出来，比如 Python 里 getattr(obj, name)() 这种动态调用，或者一个局部变量的方法。认不出来的怎么办？单独隔离到 dropped-calls.json 存档、分好类（内置函数/局部变量方法/裸名字……），不混进调用图里装作知道。图里的每条边都是有把握的。
另外两个边界：不支持的语言文件（.java、.json、.md 等）不进调用图；测试文件、vendor、node_modules 这类默认跳过。

## 2. 每个文件都有文档？每个函数都有？都有行号？
每个文件：有，保证有。 上面说了，"每文件一张卡片"是构造上保证的，缺了会显式记账。

每个函数：条目一定有，散文尽力有。 这句话是理解整个系统的钥匙。每个函数的文档条目分两半：

结构那一半（一定有，程序填的）：函数名、签名、起止行号、它调用谁、谁调用它、调了哪些外部库。这些从调用图里直接搬过来，不经过大模型的手。
散文那一半（尽力有，模型写的）：干什么用（purpose）、数据怎么流（data_flow）、调用关系的人话解释（relations）。deep 模式下模型逐个函数写；如果模型那次抽风没写出来，这三个字段可以是空的，但条目本身和行号还在。
每个函数都有行号记录：是的。 看真实例子，这是 demo 项目里 Worker.run 在调用图里的登记：


"app.worker.Worker.run": {
  "file": "app/worker.py",
  "lineStart": 10, "lineEnd": 13,
  "signature": "def run(self)",
  "className": "Worker", ...
}
第 10 到 13 行，解析器量出来的，手册里显示的"（lines 10–13）"就是它。

## 3. "每个事实带行号，写错了谁都能指出来"是什么意思？
意思是：手册给了你"核对答案的页码"。

传统 AI 生成的文档最大的问题是——它说错了你都不知道，因为你没法核对：它说"这个函数会重试三次"，你想验证，只能自己通读源码，成本高到没人去验，于是错误就一直留着。

Handbook 的手册里，每个函数条目都挂着"第 10–13 行"这种锚点，而这个锚点不是模型写的，是解析器量的。于是核对变得很便宜：手册说"Worker.run 会循环取任务直到队列为空"，你不信？打开 worker.py 翻到第 10 行，四行代码扫一眼——对就是对，错就是错，任何人 30 秒能戳穿一个错误。

所以那句话的完整含义是：散文（模型写的部分）可能讲得不好，但每句话旁边都贴着地址，验错成本从"通读全库"降到"按行号抽查"——这就使得错误留不住，因为发现太容易了。

## 4. 调用关系是怎么抽成"一张调用图"的？
拿真实例子走一遍。demo 项目里 Worker.run 的代码是：


def run(self):                        # 第 10 行
    while self.queue.size() > 0:      # 第 11 行
        task = self.queue.pop()       # 第 12 行
        self.execute(task)            # 第 13 行
第二遍扫描到这三处调用时，套规则去认：

self.execute(task) → 形状是"self.方法名()"→ 查名册：Worker 类自己有 execute 方法吗？有 → 记一条边：Worker.run → Worker.execute，类型 self_method（调自己的方法）。
self.queue.pop() → 形状是"self.属性.方法名()"→ 查第一遍学到的：self.queue 是什么类型？TaskQueue → TaskQueue 有 pop 吗？有 → 记边：Worker.run → TaskQueue.pop，类型 self_attr_method（透过成员对象调过去）。
类似还有两条规则：参数方法（参数注解了类型就能顺着认下去——demo 里 `Worker.__init__(self, queue: TaskQueue)` 正是靠这条让 `self.queue` 有了类型）和 import 追踪（from pkg import helpers; helpers.do() 能认出指向我们自己的 pkg/helpers.py，而 os.getpid() 认出是外部边界调用）。
认不出的（比如 print()）→ 丢进隔离区，不进图。
每认出一条，就记下"谁 → 谁、第几行、是不是 await"。全库扫完，把所有函数节点 + 所有边攒起来，就是 graph.json——这就是那张图。看它记下的真实内容：


{ "callerId": "app.worker.Worker.run", "calleeId": "app.queue.TaskQueue.pop",
  "callType": "self_attr_method", "line": 12, "raw": "self.queue.pop" }
所谓"一张图"，就是几百上千条这样的边 + 节点表。后面一切都吃这张图：章节按它排顺序、函数文档的"谁调用谁"从它来、agent 地图的联动提示也从它来。

## 5. "给 agent 用的 SKILL 地图"生成了什么？在哪？怎么看？
生成的是一个文件夹的 markdown 文件，两种形态：

形态一：agent 定位索引（跑 handbook render --agent-site 时生成）
位置：<work目录>/handbook/agent/，比如你仓库里现成的：

形态二：SKILL 技能包（跑 handbook skill 时生成），就是把手册重新打包成 Claude Code 能直接挂载的标准技能格式：SKILL.md + references/ 文件夹。demo 的成品在 examples/work/demo/skill/。

所以"地图"不是什么可视化大图，就是一组结构固定、字段可靠、agent 读起来极其省 token 的 markdown 索引页。

## 7. "事实和叙述分层"，大白话展开
打个比方：这本手册是测量员和作家合写的。

测量员（静态分析）负责量数字：这个函数在第 10 行、它调用了那三个函数、这个类有这几个属性。量完直接进档案。
作家（大模型）负责在档案旁边写故事："这个函数像流水线工人，从队列取一个任务干一个"。
关键制度是：作家没有档案的写入权限。

落到代码层面是这么实现的：每个函数的文档条目，结构字段（行号/签名/调用关系）由程序从 graph.json 里直接复制进去；模型返回的 JSON 里，只有 purpose、data_flow、relations 三个散文字段会被合并进条目——它哪怕在回复里信誓旦旦说"这个函数在第 999 行"，那个数字也根本没有入口能写进手册。

为什么这个分层是"防线"？因为大模型的毛病是一本正经地编造细节，而它最爱编的恰恰是行号、函数名、调用关系这类"看起来很具体"的东西。分层之后：

编不了事实——事实通道物理隔离；
散文写烂了——顶多是"讲得平庸"，而且旁边就贴着行号（第 3 题），一查便知；
连"解析失败"都不许它补——认不出的调用进隔离区，宁可承认不知道，也不让模型猜。
一句话总结：能验证的部分绝不交给模型，交给模型的部分永远可验证。 这就是第一道防线。
