壹卷首
STAGE-2 · 我们都遇到过

文档的三种死法

新人第一周
「架构图是两年前画的，wiki 最后编辑于上个季度——最后还是靠拉着老同事读了三天代码。」
写文档的人
「写完那天就开始过期。没有任何机制把代码变更同步回文档，于是大家默契地不再看它。」
用 AI 改代码的人
「Agent 改了 JSON 解析器，漏了镜像的 XML 解析器和两处提示词模板——文本搜索找不全散落的关联点。」

共同根因：文档是一次性的手工快照，而代码是持续变化的活物。

贰痛点
STAGE-3 · 解法

不是「生成文档」，是闭环

手册帮 agent 找全改动点；改完的代码又通过 resync 滚回手册。文档第一次有了自我更新的回路。

叁闭环
STAGE-4 · 核心设计 ①

事实与叙述，分层负责

事实层

DETERMINISTIC · 静态分析产出
  • 函数、方法、行号、签名 —— tree-sitter 解析
  • 调用边：self / 属性 / 参数 / 跨模块，逐条解析
  • 解析不了的调用隔离存档，绝不混入图中
  • Python · TypeScript · Go · Rust · Shell
LLM 只在事实之上写作

叙述层

LLM · 大白话散文
  • 每个文件一张"卡片"：用途、角色、生命周期
  • 每个函数：干什么 / 数据怎么流 / 谁调用它
  • 章节与系统总览：自底向上，先子后父
  • 中文 / 英文叙述随时切换

所以：散文可以平庸，事实不会说谎。行号、调用关系这些"锚点"永远来自代码本身。

肆分层
STAGE-5 · 核心设计 ②

章节结构不是生成的，是评审出来的

「骨架医生」循环：actor 提出结构修改 → 工程师 / 架构师 / 读者三个角色化评审并行审核 → 机械校验后才落地 → 受影响文件重新归位。评审自己出故障？按 REJECT 处理——坏掉的评审员永远无权放行。

伍对抗
STAGE-6 · 核心设计 ③

面对真实世界的模型：降级，而不是崩溃

三级降级

整批 → 单文件 → 按函数分块

读文件失败自动降一级重试；仍失败就记诚实的空卡片并计入覆盖率报告——绝不静默丢文件。

确定性回退

每个 LLM 步骤都有非 LLM 的备胎

编组失败退回调用图拓扑序；叙述失败退回章节描述。一次模型抖动不会毁掉一次构建。

内容哈希缓存

重跑只付「变化」的钱

章节叙述按内容哈希缓存；resync 后只有受影响的章节重新生成，其余全部命中缓存。

断点续跑

崩了就接着跑，--resume

卡片逐批落盘、产物全部 schema 校验带版本号；任何阶段可独立重跑，损坏产物大声报错。

陆韧性
STAGE-7 · 产出

一次生成，两种读者

FOR HUMANS · 手册站点

像读书一样读代码库

系统总览 → 按执行顺序排列的章节 → 每个文件的走读与函数细节。自包含 HTML（多页或单文件 57KB），双击即开，离线可用，深色模式，还有跨章节的状态寄存器表——全局状态在哪读在哪写，一目了然。

FOR AGENTS · 定位索引 + SKILL 包

给 AI 一张「改哪里」的地图

每章一个定位块：职责 / 入口概念 / 涉及状态 / 范本文件 / 强共变提示（改 A 必改 B）/ 核心文件。打包成标准 SKILL 挂给任何 agent，内容哈希做漂移检测——代码变了，手册页会自己「举手」说我旧了。

同一份事实，两种表达。团队新人和 Claude Code 用的是同一本手册。

柒产出
STAGE-8 · 闭环的右半边

手册不止被读，还参与改代码

handbook plan

手册驱动的变更定位

只读 agent 先用手册路由（哪些章节、哪些状态在射程内），再读真实源码确认，最后输出逐字精确的编辑计划：old→new 文本块 + 机器可读的变更声明（改了哪些函数、新增哪些、删除哪些）。执行器可以闭眼替换。

handbook resync

变更落地，手册前滚

对比新旧调用图指纹 → 只为变化的文件重写卡片 → 重排受影响章节 → 叙述走缓存增量更新。删掉的文件连它的卡片一起清掉，绝不留幽灵证据。全程崩溃安全：没跑完，基线不动。

这就是和「一次性文档生成器」的本质区别：生成 → 使用 → 回写，是一个可持续的循环。

捌循环
STAGE-9 · 这不是玩具

工程可信度

9包 · 严格单向依赖的 pnpm monorepo，LLM 与确定性代码按包隔离
167测试全绿 · 全部离线运行，零 API key，含 mock 全管线 E2E
3轮对抗评审 · 独立评审 agent 找茬，33 项缺陷全部修复并有回归测试
5语言 · 纯 WASM tree-sitter，安装零编译
100%可复现 · 产物 schema 校验带版本号，任意阶段独立重跑
对抗评审是怎么做的

每轮派独立的「找茬 agent」通读源码 + 对着构建产物写复现脚本验证，只报告可复现的真缺陷（含高危：JSON 解析错位、并发限流竞态、增量基线破坏）。修复后下一轮先复核再扫新，直到扫描干涸。这套机制本身，就是产品里 actor-critic 思想的自我实践。

玖可信
STAGE-10 · 吃自己的狗粮

它给自己写了本手册

78 个源文件 → 21 个语义化章节（call-graph-assembly、planner-agent、llm-channel…），全中文叙述，未归位文件 0。系统总览开篇是模型自己写的——

「这是一套命令行工具，把代码库自动翻译成人类可读的手册和 AI 代理可用的技能包。……第一阶段静态扫描代码，拼出函数调用关系网；第二阶段逐文件请大模型写用途卡片……第三阶段自底向上撰写叙述，经多角色 AI 审查反复打磨。」

章节里甚至有恰当的比喻：语言适配器注册表被写成「酒店前台各国翻译员的名册」。这是给普通读者的文档该有的样子。

拾实证
STAGE-11 · 五分钟上手

三条命令，从仓库到手册

# .env 里放 OPENAI_API_KEY（任意兼容端点：官方 / vLLM / 内部代理）
handbook analyze --source ~/code/myproj --work work/myproj # ① 静态分析，免费冒烟
handbook generate --source ~/code/myproj --work work/myproj --narrate-lang zh
handbook render --work work/myproj --html --agent-site # ③ 手册站点 + agent 索引
# 代码变更后：
handbook resync --case case1 --work work/myproj # 增量前滚，只付变化的钱

成本可控

brief 模式先试水，deep 模式再精读；--resume 断点续跑；叙述缓存让重跑近乎免费。

不挑模型

OpenAI 兼容即可。内置 mock 端点让 CI 和演示零 token 跑全流程。

不挑仓库

五种语言自动探测混合分析；大库自动分章，小库可手写骨架逐函数精修。
