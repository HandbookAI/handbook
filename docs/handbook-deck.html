04 · 关键疑问

不是替代 Claude Code，是给它装外挂记忆

每次现场探索 → 一次沉淀复用

agent 每接一个任务都要重新定位一遍：grep、读文件、猜错、再来一遍。费的不只是 token——每一轮都会把整段对话重发一次，成本随轮次快速放大。而整库装不进上下文窗口。Handbook 是有上限的路由层，一次梳理，全队每个任务复用；它字节稳定，还能吃 prompt 缓存。

结论散在对话里 → 可核对的资产

现场探索的结论随对话即焚，事后无法核对。手册的每个事实带行号，讲错了任何人都能指出来、改回来。

散落的改动点 → 一张清单

定位块把「碰哪些全局状态、改了源文件必须同步改哪个测试、同子组还有哪些文件、新增同类照哪个范本写」列成固定字段，字段为空同样是结论。本仓 20 章里有 14 章列出了源文件↔测试的强共变配对。它按调用图与命名推导，所以标注「编辑前请核实」——它不读 git 历史，纯口头传承的约定抓不到。

改码前查图，改完回写——Handbook 是 coding agent 的地图与记忆，不是它的对手。

05 · 工作方式

生成 → 使用 → 回写，一个闭环

左半边是「生成文档」，右半边才是价值所在：手册帮 agent 找全改动点，改完的代码又把手册滚到最新。它会不会也过期？会——如果 resync 没人跑。所以把它做成 CI 任务：合并即更新，新鲜度从「靠自觉」变成「靠流水线」。

08 · 为什么敢信

三道防线，挡住大模型的不靠谱

01 · 事实与叙述分层

模型无权碰事实

行号、函数清单、调用关系全部来自 tree-sitter 静态分析；解析不了的调用隔离存档而不是混进图里。LLM 只负责在事实之上写大白话。散文可以平庸，锚点不会说谎。

02 · 结构靠评审出来

三个角色互相拆台

章节结构由「骨架医生」循环打磨：提案 → 工程师 / 架构师 / 读者三个评审并行审核 → 机械校验后才落地。评审输出损坏或格式非法时，一律按「不通过」处理——出错的评审员，不能成为放行的理由。

03 · 降级而不是崩溃

每一步都有备胎

模型调用失败时逐级缩小请求：整批 → 单文件 → 按函数分块，三级降级；叙述失败退回确定性文本；阶段 3 的叙述与寄存器按内容哈希缓存，卡片支持 --resume 断点续跑。一次模型抖动，毁不掉一次构建；失败会被记录在覆盖率报告里，不会虚报。

11 · 可验证性

别信我，自己核

30 秒戳穿一个错误

每个函数条目挂着行号，而行号是解析器量的、模型碰不到。手册说 Worker.run 循环取任务直到队列空——打开 worker.py 第 10–13 行，四行代码，对就是对。

评审记录在仓库里

9 轮对抗式评审、133 项发现，报告全在 docs/internal/review/，每条附可运行的复现脚本。想知道它哪里坏过，自己翻。

离线跑通，零 token

bash examples/run-demo.sh 走内置 mock，不联网、不花钱，端到端出一本手册加一个 SKILL 包。不用先信我才能试。

过期它自己会说

SKILL 里存了每个源文件的内容哈希，handbook validate 重算一遍就能点出哪几页已经落后于代码——它不会装新鲜。

边界 · 我们不装： 小仓库不划算，几十个文件直接读更省；目标有字面量可搜时 grep 无敌；过期的手册比没有手册更贵，所以 resync 必须有人跑； 叙述质量取决于所接的模型，但行号与调用关系不受影响；纯口头传承的约定它抓不到（不读 git 历史）； 本仓有 2 个文件被服务商网关按内容拦下，我们没绕过——如实降级成空卡片并在覆盖率里点名。
